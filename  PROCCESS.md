# PROCESS.md

## 1. Недельный цикл

Рабочая итерация:

**четверг → следующий четверг**

В четверг:

- выступаем со стендапом
- подводим итоги прошлой недели;
- проверяем незавершённые задачи;
- выбираем задачи на новую итерацию;
- обновляем GitHub Project.

---

## 2. GitHub Project

Основной Project:

`Tess Development`

Используем поля:

- Status
- Iteration (номер недели разработки)
- Area
- Priority
- Assignee

Основные статусы:

- Backlog
- Todo
- In Progress
- Review
- Blocked
- Done

---

## 3. Views

Используем:

### Current Week
Главная рабочая доска текущей итерации.

### My Work
Персональные задачи участника.

### By Area
Обзор задач по Backend / iOS / Android / Web Studio / Design / Research / Infrastructure.

### Backlog
Незапланированная работа и будущие задачи.

### Roadmap
Крупные этапы и features проекта.

---

## 4. Планирование недели

На новую итерацию берем только задачи, которые:

- понятны;
- имеют Assignee;
- имеют Area и Priority;
- достаточно малы для выполнения за несколько дней;
- не имеют неизвестного blocker.

Статус таких задач:

`Todo`

Не планируем всю доступную неделю на 100%: оставляем время на review, интеграцию и неожиданные проблемы.

---

## 5. Работа с задачами

Обычно у одного человека одна основная задача в `In Progress`.

Не начинаем новую большую задачу, если текущую можно сначала закончить.

Если задача слишком большая — разбиваем на sub-issues.

Parent issue используется для feature или общей инициативы.

Пример:

```text
Market research
├── Research — Alice
├── Research — Bob
├── Research — Charlie
└── Synthesize findings
```
---

## 6. Blocked

Если продолжать работу невозможно:

  1. перевести Issue в Blocked;
  2. описать причину;
  3. сообщить команде.

Blocker не должен оставаться неизвестным до следующего стендапа.

---

## 7. Review

Когда работа закончена и PR готов к проверке:

`In Progress → Review`

После merge связанный Issue закрывается и переходит в Done.

---

## 8. Automation

GitHub Project автоматически:

  - добавляет Issues из репозитория;
  - добавляет sub-issues;
  - назначает новым items статус Backlog;
  - переводит закрытые Issues в Done.

Команда вручную управляет:

  - Todo;
  - In Progress;
  - Review;
  - Blocked;
  - Iteration;
  - Priority.

---

## 9. Discord co-working

Раз в неделю проводим совместную рабочую сессию.

Примерный формат:

  - 10 мин — короткая синхронизация;
  - 50 мин — самостоятельная работа;
  - 10 мин — перерыв;
  - 35 мин — интеграция / pair work / review;
  - 15 мин — короткое demo результатов.
  - 
Discord-сессия предназначена для работы, а не для длинного status meeting.

---

## 10. Ретроспектива

Раз в две недели обсуждаем:

  - что помогает работать;
  - что мешает;
  - что изменить.

Выбираем максимум 1–2 изменения процесса и проверяем их в течение следующих двух недель.

---

## 11. Главный принцип
GitHub Project должен отражать реальное состояние проекта.

Процесс нужен для того, чтобы:

  - видеть прогресс;
  - быстро замечать blockers;
  - уменьшать зависимости между людьми;
  - регулярно доводить задачи до результата.
