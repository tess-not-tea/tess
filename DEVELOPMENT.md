# DEVELOPMENT.md

## 1. Модель разработки

Используем trunk-based development с короткоживущими ветками.

Основная ветка:

`main`

Прямой push в `main` не используем.

Работа проходит по схеме:

Issue  
→ branch  
→ Pull Request  
→ review  
→ merge  
→ issue closed

---

## 2. Issue-first workflow

Основная единица работы — GitHub Issue.

Issue должна:

- находиться в `Tess Development`;
- иметь Assignee;
- иметь Status;
- иметь Iteration;
- иметь Area;
- иметь Priority.

Крупные задачи можно разбивать на sub-issues.

---

## 3. Ветки

Для каждой задачи создаём отдельную ветку.

Формат:

`<type>/<issue-number>-<short-description>`

Примеры:

`feat/42-ios-button-rendering`  
`fix/57-schema-validation`  
`docs/63-add-research-report`

Типы:

- `feat`
- `fix`
- `refactor`
- `docs`
- `test`
- `chore`

Ветка должна жить недолго.

Ориентир: 1–3 дня.

Если задача требует сильно больше времени, её стоит разбить.

---

## 4. Pull Requests

Каждое изменение в `main` проходит через PR.

PR должен:

- решать одну понятную задачу;
- быть связан с Issue;
- быть достаточно небольшим для нормального review.

В описании PR используем:

`Closes #<issue-number>`

Например:

`Closes #42`

После merge Issue автоматически закрывается и переходит в `Done`.

---

## 5. Review

Перед merge нужен минимум один review.

Проверяем:

- корректность;
- понятность;
- соответствие архитектуре;
- влияние на общие контракты;
- наличие необходимых тестов;
- отсутствие случайных изменений.

Review — это проверка решения, а не человека.

---

## 6. Статусы

Используем:

- `Backlog` — задача ещё не готова;
- `Ready` — можно брать;
- `In Progress` — работа идёт;
- `Review` — PR готов и ждёт проверки;
- `Blocked` — работа остановлена внешней зависимостью;
- `Done` — задача завершена.

Разработчик сам поддерживает актуальный статус задачи.

---

## 7. Definition of Done

Задача считается завершённой, если:

- acceptance criteria выполнены;
- код/документация готовы;
- PR прошёл review;
- PR merged;
- CI не сломан;
- Issue закрыта;
- GitHub Project отражает статус `Done`.

`Работает у меня локально` не означает `Done`.

---

## 8. Общие контракты

Изменения, которые затрагивают несколько частей системы, нельзя делать изолированно.

Особенно это касается:

- Application Schema;
- API;
- Actions;
- Navigation;
- Validation;
- Workflows;
- Permissions.

Перед такими изменениями нужно согласовать контракт с затронутыми разработчиками.

---

## 9. Monorepo

Все части Tess находятся в одном репозитории.

Предполагаемая структура:

```text
apps/
  web-studio/
  ios/
  android/

services/
  backend/

packages/
  schema/
  fixtures/

docs/
  research/
  architecture/

.github/
```

## 10. Исследования и документация

Результаты исследований и важные материалы храним в репозитории.

Пример:

`docs/research/`

Если результат работы должен сохраниться для команды, он не должен существовать только в Telegram или Discord.
